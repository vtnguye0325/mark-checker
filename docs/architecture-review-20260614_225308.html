Candidate 1

Unify format_input / format_fields into a single FormattedMark

Strong

Files

backend/app/services/text_formatter.py backend/app/routes/predict.py backend/app/routes/explain.py tests/test_text_formatter.py

Problem — Shallow Dual Interface

text_formatter exports two separate entry points for the same underlying operation: format_input() returns a joined string (for /predict), and format_fields() returns a list (for /explain). The caller — the route — must know which to call, and must trust that they stay in sync. A test in test_text_formatter.py exists precisely to assert their consistency, which is the smell: an invariant encoded in a test that should be encoded in a type.

The root cause: field boundaries must be preserved for leave-one-out attribution (descriptions can contain ". "), so re-splitting the joined string would be wrong. But instead of solving this once inside the module, it's split across two exported functions and a consistency test.

Deletion test: delete format_input. Routes calling it fail. But the complexity doesn't vanish — it migrates: routes would call format_fields and join themselves. The invariant disappears from the module and reappears in every caller. That's the sign it belongs inside.

Solution

Replace both functions with a single FormattedMark value object. Callers call one function — format_mark(mark, description, nice_class, ...) — and get back a struct with both .text (joined string) and .fields (list). The seam is now a single type, not two functions. The consistency invariant is gone — it was never possible to have them diverge if there's only one call.

Benefits — Locality & Leverage

  • Locality: the field/string duality is a single concept; it now lives in one place.
  • Leverage: routes call one function and get everything they need; the consistency test is deleted.
  • Testability: test the shape of FormattedMark once; route tests become trivially simple.
  • RAG-ready: when RAG retrieval needs to pass formatted text to the retriever, it takes FormattedMark.text — no decisions to make.

Candidate 2

Extract pipeline orchestration into useTrademarkPipeline

Strong

Files

frontend/src/App.jsx frontend/src/hooks/useTrademarkPipeline.js (new)

Problem — Business Logic Entangled in a React Component

App.jsx holds 6+ state variables and directly orchestrates the three-step predict → explain → analyze pipeline with chained .then() calls. This is business-layer logic — sequencing, error recovery, cancellation — embedded in a presentation component. The seam between "how the UI looks" and "how the pipeline runs" is non-existent.

The result: you cannot test pipeline sequencing (e.g., "if /explain fails, /analyze is skipped") without rendering a React component. The AbortController setup, the loading flags, and the chained API calls are interleaved with JSX rendering — no locality, low leverage.

Deletion test: remove the pipeline orchestration from App.jsx. The complexity re-appears at every call site (or nowhere, meaning the app stops working). It earns its keep.

Solution

Extract all sequencing logic into a useTrademarkPipeline() custom hook. The hook owns: AbortController lifecycle, the three fetch calls in order, all loading/error state, and result accumulation. App.jsx calls const { submit, state } = useTrademarkPipeline() and passes state down as props. The hook has no JSX. The component has no fetch logic.

Benefits — Locality & Leverage

  • Locality: all pipeline logic — sequencing, cancellation, error handling — lives in one file.
  • Leverage: App.jsx shrinks from 157 lines to ~60. State props become a single state object.
  • Testability: test the hook with renderHook — no component rendering needed. Test "explain fails → analyze skipped" purely in JS.
  • RAG-ready: when the pipeline adds a retrieval step, it's one place to change.

Candidate 3

Extract parseLegalAnalysis from LLMAnalysis.jsx

Worth Exploring

Files

frontend/src/components/llm/LLMAnalysis.jsx frontend/src/lib/parseLegalAnalysis.js (new)

Problem — Parser Buried Inside a Renderer

LLMAnalysis.jsx at 178 lines is the largest frontend file. But almost all of that mass is parsing logic, not rendering logic: parseSections() splits on markdown headers, then per-section parsers extract verdict tiers, spectrum bullets, and signal blocks. This is domain logic — it understands the structure of a legal analysis response — and it's trapped inside a React component.

The parser is untestable without rendering. If DeepSeek's output format changes, you find out when the UI breaks in a browser — not from a failing unit test.

Solution

Extract parseLegalAnalysis(rawText) as a pure function in frontend/src/lib/parseLegalAnalysis.js. It returns a structured object: { sections: [{type, title, content, parsed}] }. LLMAnalysis.jsx calls the parser and renders the result — no parsing logic remains in JSX. The parser can be unit-tested with plain strings; the component becomes thin.

Benefits — Locality & Leverage

  • Locality: all LLM output parsing in one JS file; rendering in another.
  • Testability: write tests like expect(parseLegalAnalysis(sample)).toMatchObject({sections: [...]}) — no React needed.
  • Leverage: LLMAnalysis.jsx shrinks to ~50 lines. New section types need changes in one parser file only.

Candidate 4

Split model_service into ModelLoader + Inference

Speculative

Files

backend/app/services/model_service.py tests/test_model_service.py

Problem — Lifecycle Mixed with Computation

model_service.py does three things: (1) resolves the model directory from env vars, (2) loads and caches the tokenizer + model + device via @lru_cache, (3) runs inference (predict_one, explain_one, _score_batch). The loading concern and the inference concern share a module, with inference functions calling _load() internally.

This makes it hard to test loading failure scenarios (model dir missing, CUDA unavailable) without running inference. Conversely, mocking _load in inference tests is awkward.

Deletion test: the current design works well at this scale. The friction is mild — hence Speculative. Consider this if the RAG layer adds a second model (e.g., an embedder), at which point the lifecycle pattern would need to generalize.

Solution

Introduce a ModelLoader protocol / class that owns lifecycle (load(), is_loaded(), device). Inference takes a loaded model as a dependency rather than calling _load() directly. The seam between loading and computing becomes explicit. This mirrors what the RAG plan will likely need for its embedding model.

Benefits

  • Locality: loading errors vs. inference errors are distinct concerns in distinct places.
  • Testability: inject a fake loaded model to test predict_one/explain_one without I/O.
  • Leverage: low — the current LRU cache approach is simpler. Recommend deferring until a second model is added.
